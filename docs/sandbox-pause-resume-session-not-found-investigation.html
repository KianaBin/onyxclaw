Sandbox 暂停恢复 Session not found 问题排查报告

报告日期：2026-08-27 环境：Huawei Cloud CCE / AgentSphere / Agent Gateway APP：OnyxClaw Cloud Runtime 问题边界已收敛
结论： 暂停恢复失败的直接原因是 AgentSphere 控制面已经返回 connect 成功，但 Agent Gateway 数据面没有该 Sandbox 的可用 session。最新 v17 在两个独立 Sandbox 上复现：控制面 connect 均成功，APP 确认等待 1 秒后再发起 Files.write，但失败请求仍持续 45 秒并返回 Session not found。同一 Sandbox、同一 token 指纹、header、domain、Gateway host 和端口，在后续 connect 中又可以立即写入成功。因此已基本排除 前端或 APP 的 token/header 管理以及固定 1 秒时序问题，核心位于 Gateway 恢复后的 session 注册、内部路由 或服务端 token/session 映射。

1. 问题背景

用户在前端执行以下流程：

进入对话
  → 点击“暂停” Sandbox
  → 点击“恢复”
  → APP 重新写入 /home/node/.openclaw/openclaw.json
  → 读取持久化 SOUL.md
  → 启动 OpenClaw 并恢复 WebSocket 对话

异常发生在恢复后的第一步数据面操作：

Sandbox.connect  → 成功
Files.write       → 等待 45 秒
Agent Gateway     → Session not found

早期反馈表现为：首次流程偶尔成功，“重置新用户”后第二轮更容易失败，手动刷新页面后又可能恢复。由于这些现象同时涉及前端状态、Sandbox ID 和 token 生命周期，最初怀疑是重置后复用了旧 session 或请求 header 携带错误。

本轮使用带安全指纹埋点的 debug v16 镜像，对新用户、同一 Sandbox 多轮恢复、重置新用户以及刷新页面重试进行了 E01～E05 五次受控测试。埋点只记录 token 是否存在、长度和 SHA-256 前 12 位，不记录凭据明文。

2.2 本轮结论

  1. 直接原因已确认：connect 成功不等于 Agent Gateway 数据 session 已可用；失败发生在控制面成功与数据面 session 可用之间。
  2. APP token/header 管理基本排除：重置后新 Sandbox 获得了新的 envd token，且失败轮与成功轮的客户端凭据和 header 完全一致。
  3. 刷新页面不是修复原因：刷新只是在更晚时间触发 fresh connect；后端 Pod、bridge 和 session map 均未重置。
  4. 服务端内部原因仍需日志细分：可能是 Gateway session 注册延迟/竞态、内部 shard 路由不同步，或服务端 token/session 映射未同步。

2.4 v17 数据直接支持的判断

  • 固定 1 秒延时不足：每个失败轮都可由“失败完成时间减 45 秒耗时”反推出 writeFile 在 connect 完成约 1.001 秒后发起，说明代码延时确实生效，但 Gateway session 仍不可用。
  • 失败不是客户端凭据固定错误：两个 Sandbox 的 envd token 指纹不同，证明重置后获得了新凭据；每个 Sandbox 内成功轮和失败轮的指纹及 header 完全相同。
  • 重新 connect 不保证修复：485faf4a… 第二次暂停后 generation 4～9 连续 6 次 connect 成功，但对应 writeFile 全部失败。
  • 同一配置会自行恢复可用：ed9a54be… generation 2、3 失败，generation 4 在未更换 Sandbox ID、token、Gateway 或端口的情况下写入成功，随后 generation 5、6 也连续成功。
  • 故障状态属于 Gateway 数据 session 生命周期：客户端没有可观察到的字段变化可以解释从失败切换为成功，需要服务端关联 session 注册、注销和 shard lookup 日志。

4. 当前连接与 Header 管理链路

Node session wrapper
只保存 sandboxId
→
Python Sandbox.connect
获取新的 SDK session
→
构造 routed Sandbox
访问固定 Agent Gateway

每次 connect 后，Python 侧都会替换：

sessions[sandbox_id] = (claimed, routed(claimed))

数据面请求当前包含或预期包含以下 header：

  • X-Access-Token：envd access token。
  • E2B-Traffic-Access-Token：traffic access token（connect 返回时存在才添加）。
  • E2b-Sandbox-Id：逻辑 Sandbox ID。
  • E2b-Sandbox-Port：envd port。

Node wrapper 本身不保存 token，文件操作会按照 sandboxId 从 Python 的最新 session map 中取 routed session。因此“前端或 Node 始终复用第一次 token”与当前实现不符。

7. 根因边界与服务端候选原因

已确认故障边界位于 AgentSphere 控制面 connect 成功 与 Agent Gateway 数据会话可用 之间：

Sandbox 管理控制台：已恢复
Sandbox.connect：HTTP 成功
                   │
                   ├─ 成功轮：Gateway session 可用 → Files.write 立即成功
                   │
                   └─ 失败轮：Gateway session 不存在 → 45 秒内持续 Session not found

APP 侧能够确认问题属于 Gateway 服务端数据 session 生命周期，但仅凭客户端日志无法再区分以下内部实现分支：

  1. session 注销/重注册竞态或最终一致性异常：pause 删除旧数据 session 后，resume 未同步完成重新注册，但控制面提前返回成功。
  2. Gateway shard 路由未同步：session 已在某个内部节点恢复，但固定 Gateway 入口仍将请求路由到查不到该 Sandbox ID 的节点。
  3. 服务端 token/session 映射未同步：客户端 token 与 header 正确，但 Gateway 登记的 session 映射仍是旧状态或暂时不存在。
  4. E2B 兼容控制面语义不足：Sandbox.connect 成功只表示恢复请求被接受，没有保证 envd 数据面已经 ready。

请服务端重点返回：控制面 connect request ID、数据 session registration ID、注销/重注册事件时间、目标 Gateway shard、实际 session lookup key、lookup miss 原因，以及成功轮与失败轮是否命中不同内部节点。 上述客户端字段只用于日志关联，不包含 token 明文。

9. 建议处置方向

根因修复应由 Gateway 服务端完成；APP 只能做体验兜底

  1. 服务端根因修复：Gateway 应保证 resume 后 session 注册、路由和 token 映射完成，再将 connect 标记为成功；或提供明确的数据面 ready 状态。
  2. 服务端可观测性：connect 响应应返回可关联的 request ID、session registration ID 或 shard 信息，避免控制面成功后无法追踪数据面。
  3. APP readiness：恢复时先执行轻量数据面 probe，成功后再写 openclaw.json，避免把 Gateway 故障误报成配置文件写入失败。
  4. APP 有界重试：遇到 Session not found 时废弃当前 routed session 并重新 connect；实验表明故障窗口可接近五分钟，不宜让单个页面请求静默阻塞整个窗口。
  5. 用户提示：明确显示“Sandbox 已恢复，但 Gateway 数据会话尚未就绪”，保留显式重试按钮和 Sandbox ID。
  6. 路由验证：服务端确认是否允许固定 Gateway URL；若 resume 可能迁移 shard，应返回并使用正确的动态路由信息。

10. 最终结论

Session not found 是恢复后 Agent Gateway 数据会话不可用的直接表现，不是 openclaw.json 写入内容错误。

v17 的两个独立 Sandbox 都在创建阶段正常写入，并在 pause 后出现“connect 成功、等待 1 秒、writeFile 持续 45 秒后 Session not found”。其中 Sandbox A 在第二轮暂停后连续 6 次 connect 成功但全部写入失败；Sandbox B 前两次失败后，在客户端字段完全不变的 generation 4 恢复成功，后续两轮暂停恢复也连续成功。App 侧 Sandbox ID、token/header 生命周期及固定 1 秒时序问题已基本排除，根因集中在 Gateway 恢复后的 session 注册、注销竞态、内部 shard 路由或服务端 token/session 映射。
